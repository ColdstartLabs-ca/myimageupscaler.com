# Mobile origin / HTML cache diagnosis (AC-4)

**PRD:** [PRD-traffic-recovery-2026-09](../../PRDs/traffic-recovery-2026-09.md) · **Date:** 2026-09-16
**Method:** the [mobile LCP fix plan](./2026-09-08-mobile-lcp-fix-plan.md) §4 — cookie-free document requests, mobile UA, recording TTFB, connection reuse, `cf-cache-status`, `x-nextjs-cache`/`x-opennext-cache`, `Age`, `Cache-Control`, `Vary`, `cf-ray`. The three-run Lighthouse baseline was **not** rerun.
**Verdict: variance REPRODUCES; cause NOT established.** AC-4 stays PARTIAL — the AC needs a reproduced _cause_ or a STOP, and neither holds yet.

## Evidence

14 cookie-free mobile requests to `https://myimageupscaler.com/` (6 spaced 3s apart, 8 back-to-back), all `200`, all identical 302,025-byte bodies, all `cf-ray … -YVR`, TCP connect ~3ms throughout.

|                                          | TTFB          |
| ---------------------------------------- | ------------- |
| min                                      | 148 ms        |
| median (n=14)                            | 633 ms        |
| max                                      | 1,986 ms      |
| over the repo's 400 ms diagnostic target | 8 of 14 (57%) |

Every one of the 14 returned `x-nextjs-cache: HIT` with `Cache-Control: s-maxage=~73,250, stale-while-revalidate=2592000`.

Two structural facts, constant across all 14:

1. **No `cf-cache-status` and no `Age` on any HTML response.** The header is not merely absent from the Worker path — `https://myimageupscaler.com/favicon.ico` returns `cf-cache-status: HIT` at 27–33 ms from the same client, so the edge does emit it when it caches. This is consistent with, but does not prove, the HTML never being served from Cloudflare's edge cache: [cloudflare-cache-setup](../../guides/cloudflare-cache-setup.md) notes Cloudflare may omit `cf-cache-status` when the Worker returns HTML directly. No edge HIT was observed; the `Cache anonymous HTML` zone rule (active since 2026-08-25) cannot directly govern the Worker's own cache (see Topology below), so its lack of warm responses is expected and is not by itself the cause.
2. **`Vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch`** on every HTML response. For the zone CDN cache, `Vary` handling depends on configuration; the [Cache Rules Vary setting](https://developers.cloudflare.com/cache/concepts/vary/) (available on all plans) can key zone-rule variants on listed request headers; an origin header the rule does not recognise follows its configured `default` action. Because zone Cache Rules do not govern a Worker's own cache (see Topology below), these RSC/Next-router headers are a _candidate_ mechanism to test — not the blanket "only `Accept-Encoding` is honoured" it was once documented as, and not the established cause.

**Observed variance, no cause claimed.** Back-to-back requests (b1–b8: 187, 1986, 1092, 354, 1229, 638, 1131, 148 ms) swing the full TTFB range with no idle gap and identical bodies, so the spread is real and not a body-size effect. What the samples **cannot** establish is where the time goes. They rule out idle eviction as the _sole_ explanation only if consecutive requests kept the entry warm, which was not measured, and no network-layer data (TCP retransmits, routing/placement, CDN timing breakdown) was captured — so "not network" is not supported. The extra time could be per-request Worker work, host/edge placement or routing variance, concurrent-request contention, or the OpenNext cache path; none of these was isolated. `x-nextjs-cache: HIT` identifies the OpenNext incremental cache, not the layer that spent the second.

## Hypothesis (not a cause)

The `Vary` handling leaving the public HTML unstored in Cloudflare's edge cache is a **hypothesis to test**, not the established cause: the absent `cf-cache-status`/`Age` is the observation, and no observed edge HIT is not proof that `Vary` is the reason. The TTFB samples above do not confirm the mechanism either. This is **not** evidence that performance caused the search decline, and the lab LCP number must not be mixed with these observed TTFB figures.

## Why no code change is proposed yet (engineering gate first; owner deploy later)

**Topology first.** This project is a Cloudflare **Worker**, not a Pages project: production deploys with `wrangler deploy` from the authoritative `wrangler.json` (`main: .open-next/worker.js`, `routes` on `zone_name`), and `scripts/deploy/steps/03-deploy.sh` runs `npx wrangler deploy`. The `pages_build_output_dir` in `wrangler.toml` is stale and is not what production deploys. `/` HTML is generated by this OpenNext Worker, and middleware runs _inside_ the Worker. If Workers Cache is enabled, its lookup runs **before** that middleware. Cloudflare's [Workers Cache](https://developers.cloudflare.com/workers/cache/) docs state that Workers Cache runs _before_ the Worker executes, is distinct from zone Cache Rules, and respects `Vary`; zone-level cache configuration (Cache Rules, cache levels, the default cached-file-extensions list) does not apply to a Worker's own cache. A dashboard Cache Rule alone must therefore **not** be promised to cache this response, and an absent `cf-cache-status` on a Worker response is not by itself evidence that a given mechanism did or did not apply. (`x-nextjs-cache: HIT` identifies the OpenNext R2 incremental cache serving the body, not a CDN hit.)

The naive code-level remedy — strip or normalise `Vary` on public HTML in `middleware.ts` — is **unsafe as-is**. The same URL serves two different bodies:

```
GET /                 → text/html,        s-maxage=73143, x-nextjs-cache: HIT
GET / (RSC: 1 header) → text/x-component, s-maxage=73143, x-nextjs-cache: HIT
```

Without a `Vary`-aware cache key, an edge entry created by an `RSC: 1` request would be served as the document to ordinary browsers (and vice versa). Dropping `Vary` trades a TTFB win for a cache-poisoning hazard on the two highest-traffic page types.

**No candidate is pre-approved and no cache mutation of any kind is recommended yet.** Neither dropping `Vary` on document responses nor a Vary rule scoped to `RSC` alone has been shown to preserve variant isolation:

- **Dropping or narrowing `Vary` only on `text/html` document responses is not a safe fallback** just because `RSC` requests keep `Vary`. Edge cache lookup happens before application middleware or response guards run, so a previously stored HTML entry can be served to an `RSC: 1` request (and vice versa) regardless of request-time checks. It is safe only with a variant-aware cache key that preserves every meaningful variation (the RSC/Next-router headers, cookies/auth state, other dimensions) and is demonstrated end to end.
- **A rule keyed on `RSC` only, leaving the other Next `Vary` headers omitted, is not proven sufficient.** Whether an unrecognised header bypasses or passes through is not unconditional — it follows the rule's configured `default` action — and any authenticated/user-specific exclusion must still hold. "RSC-only" is a hypothesis to test against the real topology, not a safe default.

**Next engineering gate (agent), not an owner choice yet:** confirm the active caching mechanism for this Worker/OpenNext runtime (Workers Cache vs the OpenNext R2/regional cache vs any zone rule), then design and run a causal isolation test in a **representative preview** (`wrangler.preview.json`, `workers_dev`, no production route) that exercises document vs `RSC` variants, authenticated vs public, cookies, and geo before **any** production rollout. Only after that test does a change get proposed; the **owner gate (AC-6, João) comes later**. Nothing about auth cookies, geo, or Next/router variants may be promised safe without that test, and an `RSC`-only rule is not sufficient on its own. The user is not being asked to choose between speculative, unsafe options now.

Per the PRD, AC-5's three comparable production runs and AC-7's field review run **only after** a João-authorized rollout of an actual change. Nothing has been deployed.

**Local shipment includes** this diagnosis, the corrected mechanism wording, the PRD/backlog updates, and the prepared regression-test scope — no `middleware.ts` change and no caching is enabled locally.
